# 生图/修图历史记录完整性增强设计

## 1. 背景与目标

当前历史记录已保存与展示图片，但关键信息不足，无法快速回溯一次操作的语义上下文。典型缺失包括：

- 缺少稳定的主标题（仅靠 prompt 截断，且由前端临时拼装）
- 缺少可读说明（尤其是修图场景的修改内容）
- 各写入入口字段不一致，历史卡片展示信息不稳定

本次目标是在不重构主流程的前提下，增强历史记录数据与展示，保证“有图 + 有语义 + 可追踪”。

## 2. 设计范围与非目标

### 2.1 范围

- 增强历史 entry 数据结构（扁平扩展，兼容旧数据）
- 统一后端写历史入口，减少字段漂移
- 调整前端历史卡片为“平衡信息密度”
- 保持旧历史文件可读可展示

### 2.2 非目标

- 不引入 history v2 大规模 schema 迁移
- 不新增独立“主标题输入框”
- 不改动历史抽屉的基础交互（预览、下载、开关）

## 3. 方案选择

采用方案 A：历史 entry 扁平增强。

理由：

- 变更小，落地快，风险低
- 与现有 `history.json` 存储方式兼容
- 便于后续渐进加字段，不阻断当前业务链路

## 4. 数据模型设计

在保留现有字段的前提下，新增标准字段。

### 4.1 保留字段（兼容）

- `id`
- `timestamp`
- `mode`
- `prompt`
- `project`
- `input_image`
- `output_image` / `output_images`
- `variants_count`
- `edit_type`

### 4.2 新增字段

- `title`: 主标题，来源固定为 `prompt` 截断（约 24-30 字）
- `description`: 说明文本
  - 修图：优先保存用户输入的修改描述原文
  - 生图：有可用说明时保存，无则为空
- `meta_tags`: 关键标签数组（模式/张数等）
- `source`: 记录来源入口（如 `generate` / `job` / `edit`）
- `schema_version`: 当前版本号，固定为 `1`

### 4.3 兼容策略

- 旧 entry 不做文件级迁移。
- 在读取返回阶段补齐默认字段，保证前端稳定渲染：
  - `title` 默认由 `prompt` 回填
  - `description` 默认空字符串
  - `meta_tags` 默认由 `mode + variants_count` 推导

## 5. 后端实现设计

目标文件：`backend/app.py`

### 5.1 统一构造函数

新增统一函数（命名可按现有风格微调）：

- `build_history_entry(...)`

职责：

- 接收不同入口的原始字段
- 统一生成新增字段与默认值
- 输出结构一致的 entry 给 `add_history(...)`

### 5.2 写入入口改造

将以下入口的历史写入统一改为走 `build_history_entry(...)`：

- 同步生图入口（含 variants）
- Lovart 异步任务完成入口
- 修图入口

### 5.3 字段映射规则

- `title`: 从 `prompt` 生成（固定规则，避免入口差异）
- `description`:
  - 修图：取修图请求中的 `description`
  - 生图：有说明则写，无则空
- `meta_tags`:
  - `mode` 对应人类可读标签（如文字生图/图片改图/局部修图）
  - 多图时附加 `N张`

### 5.4 读路径增强

在历史读取过滤函数中，对旧数据做“返回前补齐”，不修改源文件内容。  
这样新前端可以只依赖统一字段渲染。

## 6. 前端展示设计

目标文件：`backend/templates/index.html`

历史卡片调整为平衡密度（三层结构）：

- 第一层：时间
- 第二层：`title`（单行省略，主视觉）
- 第三层：`description`（有则显示，单行省略）
- 底部：`meta_tags`（保留模式/张数的快速识别能力）

交互保持不变：

- 缩略图点击预览
- 下载按钮
- 抽屉开关

降级策略：

- 老数据缺少 `description` 时不渲染该行，不产生空白占位

## 7. 错误处理

- 历史写入失败不影响主流程结果返回（保留现有容错）
- 新字段构造均提供空值兜底，防止前端渲染异常
- 旧数据补齐逻辑必须幂等且无副作用

## 8. 测试与验收

### 8.1 功能验收

- 生图完成后：历史卡片显示时间、标题、说明（若有）、标签
- 修图完成后：历史卡片显示时间、标题、修图说明、标签
- 历史旧数据可正常展示，无 JS 错误

### 8.2 回归范围

- 同步生图链路
- 异步 jobs 生图链路
- 修图链路
- 历史抽屉打开、预览、下载

### 8.3 兼容验收

- `history.json` 中新旧 entry 混合时，前端展示稳定

## 9. 实施顺序

1. 后端增加统一历史 entry 构造与旧数据补齐
2. 替换三类历史写入点为统一构造
3. 前端卡片渲染读取 `title/description/meta_tags`
4. 本地回归三条链路与历史交互

## 10. 风险与缓解

- 风险：部分生图入口没有可用说明字段，导致 description 不连续  
  缓解：允许为空，先保证修图说明完整；后续再按入口补齐来源

- 风险：旧数据格式差异造成前端条件分支变多  
  缓解：在后端读取阶段统一补齐，前端只读标准字段
